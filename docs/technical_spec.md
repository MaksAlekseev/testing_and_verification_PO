# Техническое задание

## 1. Введение

Разрабатываемая программа "Office Booking" предназначена для учета бронирования
переговорных комнат и рабочих мест в офисе. Приложение используется сотрудниками
офиса для выбора ресурса, даты, времени и цели бронирования.

## 2. Основания для разработки

Основанием является практическая работа N 1 по дисциплине "Тестирование и
верификация ПО". Продукт должен быть пригоден для последующего тестирования
другой командой методом "черного ящика".

## 3. Назначение разработки

Цель разработки - создать простое настольное приложение, на котором можно
отработать подготовку технической документации, составление тест-кейсов,
выявление дефектов и оформление результатов тестирования.

## 4. Требования к программе

### 4.1. Функциональные требования

- Пользователь должен видеть список доступных переговорных комнат и рабочих мест.
- Пользователь должен создавать бронь с указанием ресурса, сотрудника, даты,
  времени, количества людей и цели.
- Пользователь должен видеть список созданных броней.
- Пользователь должен отменять выбранную бронь.
- Пользователь должен сохранять брони в локальный файл.
- При повторном запуске приложение должно загружать ранее сохраненные брони.

### 4.2. Требования к надежности

- Приложение должно обрабатывать некорректный ввод без аварийного завершения.
- Сообщения об ошибках должны отображаться в диалоговых окнах.
- Данные должны сохраняться в локальном CSV-файле.

### 4.3. Условия эксплуатации

- Операционная система: Windows 10/11.
- Для запуска `.jar`: установленная Java 8 или новее.
- Для сборки `.exe`: JDK 14 или новее.

### 4.4. Требования к совместимости

Приложение должно запускаться на Windows при наличии Java Runtime Environment.
Исходный код должен компилироваться JDK 8 или новее.

## 5. Требования к интерфейсу

Главное окно содержит:

- выпадающий список ресурса;
- поля ввода сотрудника, даты, времени, количества людей и цели;
- кнопку добавления брони;
- кнопку отмены выбранной брони;
- кнопку сохранения;
- таблицу текущих броней.

## 6. Критерии приемки

Продукт считается принятым для целей практической работы, если:

- приложение запускается;
- пользователь может создать и увидеть бронь;
- пользователь может сохранить данные;
- документация содержит техническое задание и описание внесенных дефектов;
- в продукт намеренно внесено от 5 до 8 дефектов разного типа.

## 7. Порядок контроля и приемки

Контроль проводится методом "черного ящика". Проверяющая команда составляет
тест-кейсы на основе требований, выполняет их в приложении, фиксирует ожидаемый
и фактический результат, а также статус прохождения.
